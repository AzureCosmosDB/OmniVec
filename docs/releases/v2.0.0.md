# OmniVec v2.0.0

Major release: optimized ingestion and nonblocking telemetry, hardened
readiness and connector contracts, and isolated registered benchmark components.
OmniVec remains public preview; this release is not a production-readiness
certification. Publication is pending release-image gates.

## Cumulative platform improvements

This tag includes all v1.2.0 and v1.2.1 improvements: nonblocking bounded
telemetry and App Insights reporting, Rust router FP32 transport and durable
model registry, direct model routing/replica balancing, bounded inline JSON
batches, Cosmos inline float-array reuse and write tuning, direct Cosmos
destination upserts and configurable chunk replacement order, native Garnet
sources and version-fenced vector writes, OneLake Iceberg/Delta and SharePoint
integration, connector recovery, hybrid search, Entra login, and the redesigned
operations/recovery console. See the [v1.2.0 inventory](v1.2.0.md) and
[v1.2.1 request-size fixes](v1.2.1.md) for their full scope.

## Breaking changes and upgrade

- Built-in Rust router `mock-embedding` and `mock-1536` aliases are retired.
  Register a model backed by the separate mock embedding service and use its
  model ID instead. The router never generates synthetic vectors.
- API startup now fails when metadata initialization fails. `/health` remains
  process liveness; `/ready` proves storage access and is used for startup and
  readiness probes. Correct storage identity/configuration rather than treating
  an unhealthy store as a successful startup.
- Use matching v2.0.0 images for API, web, ingestion, worker, router,
  pipeline-worker, search and OneLake watcher. Enabling mock benchmarks also
  requires the three new source/model/destination images and an admin token.
  Mock benchmarks are disabled by default. Existing deployments are not
  automatically upgraded by publishing this release.
- Existing full Cosmos upsert, chunk replacement, Garnet version/tombstone,
  and best-effort telemetry semantics remain unchanged; see the prior upgrade
  notes before upgrading from versions older than v1.2.0.

## Fixes

- Fail startup explicitly when storage initialization fails. Add bounded,
  cached `/ready` storage checks; Helm startup/readiness probes use `/ready`,
  while `/health` remains the liveness endpoint.
- Preserve source, destination and model attribution in nonblocking native
  inline ingestion metrics.
- Normalize Garnet endpoints consistently across API validation and .NET
  ingestion/writers. Correct the classic portal Garnet wizard and connector
  contracts; expand replay, checkpoint, tombstone and cancellation regressions.
- Honor OpenAI-compatible base64 embedding responses in the pipeline worker,
  with finite-vector validation and little-endian FP32 encoding.
- Prevent delayed connection-guide callbacks from dereferencing a portal
  view that has already been removed.
- Correct mock Helm pod labels to satisfy Deployment selectors and ingress
  policies, and cancel sibling mock workers promptly when a batch fails.
- Align core network policies with the workload namespace, API/web target
  ports and router labels. Keep Garnet source creation in
  the CLI aligned with the shared portal connector contract.

## Registered mock benchmarks

Register a mock source, mock embedding model and mock sink through the portal,
then create an inline, truncate pipeline. Configure document count, exact
source text bytes, generation rate, embedding dimensions, simulated latency
and sink acceptance rate. Zero rate means unlimited; limited sinks return
HTTP 429 with retry guidance instead of silently dropping excess requests.

The feature is disabled by default. Enable `api.mockBenchmark.enabled`;
use `api.mockBenchmark.shardCount` for isolated producer/receiver partitions.
Each pipeline has one leased runner and each receiver has one replica.
JSON remains the default model transport; FP32 is an explicit source option.
The FP32 path transfers every vector value over HTTP from model to runner,
and again from runner to sink, with payload and finite-value validation.

Sink metadata is cached rather than read for each batch. Configure
`api.mockBenchmark.configRefreshSeconds` (default 300); independent expiration
jitter is 80-100% of that interval. Configuration changes can therefore take
up to the configured interval to become visible. Pipeline discovery and
periodic lease/checkpoint operations remain; these are not per-batch writes.

Mock vector generation runs in a separate Rust `docgrok-mock-embedding`
image, like other model services. The Rust `docgrok-router` handles registration
and routing, forwarding full FP32 responses without generating vectors itself.
The source and destination run in separate .NET `omnivec-mock-source` and
`omnivec-mock-destination` images. The control-plane API does not generate
documents, execute mock batches or accept vectors. All three components and
the Rust router were deployed and benchmarked together.

## Repeated 150K+ documents/s result

Three simultaneous portal-registered pipelines each accepted 1,000,000
documents with 8-byte source text and full 1,024-dimensional FP32 vectors.
Each used batch size 1,024 and concurrency 8, with unlimited source/sink
rates and zero simulated model latency.

| Run | Accepted documents | Aggregate elapsed | Aggregate documents/s |
|---|---:|---:|---:|
| Corrected-image repeat 1 | 3,000,000 | 19.912 s | 150,662.9 |
| Corrected-image repeat 2 | 3,000,000 | 19.368 s | 154,894.7 |
| Corrected-image repeat 3 | 3,000,000 | 19.018 s | 157,745.3 |

All three runs completed with zero recorded throttles and no reported run
errors. Each transferred 12,288,046,896 bytes of runner-to-sink binary bodies,
including vector headers. That figure excludes model-to-runner traffic and
HTTP overhead. Aggregate elapsed is latest finish minus earliest start,
not the sum of individual pipeline rates; metadata setup is excluded.

The result is **aggregate synthetic throughput across three pipelines**,
not single-pipeline throughput, real embedding inference or persisted vector
throughput. Mock models emit deterministic synthetic vectors; sinks validate
and acknowledge them without persisting vectors. No GPU inference was used.
One partition used ordinary CPU nodes; the other two used CPU resources on
two existing A100 nodes to avoid CPU contention, without requesting GPUs.
The measured range is 150,663-157,745 documents/s (median 154,895), not a
capacity guarantee. All three pipelines were paused after each repetition.
The final images preserve reset timestamps exactly across .NET and Python
metadata readers so reset-generation receipts have matching identities.

The registered shard-1 pipeline was also reset and run alone three times

Each run accepted 1,000,000 documents and transferred 4,096,015,632 bytes

The configuration remained 8-byte text, 1,024D FP32, batch 1,024 and concurrency
8. Its source and destination used CPU resources on existing A100 node 007;

| 1 | 1,000,000 | 8.865 s | 112,803.2 |

## Deployment and remaining limitations

Use matching versioned images only after publication succeeds. Existing
deployments are not automatically upgraded. Benchmark-specific node pinning
is not a default Helm configuration. The unrelated DSE-Qwen2 adapter and
AKS infrastructure experiments are excluded.

Mock sink deduplication and rate state are memory-only; this is not a durable
exactly-once destination. Live OneLake/SharePoint acceptance has not been
established by the mock benchmark or connector unit regressions. Other
v1.2.0/v1.2.1 limitations remain unless explicitly addressed above.
Real Harrier inference and persisted-vector throughput must be measured
separately from these synthetic results.

The 4,000 persisted documents/s target remains unmet; it is not a release
capacity claim. Managed Garnet allocation and a complete healthy queued
Garnet workload matrix remain unverified. API resource sizing must still match
deployment load; readiness does not prove every integration's correctness.

Reviewed experiments remain excluded: AKS GPU-count/zone pinning would fix
all deployments to availability zone 3 and remove autoscaling flexibility;
the DSE-Qwen2 OpenAI adapter lacks release validation and strict input handling.
Their local changes are preserved for separate work.

## Release validation

Fresh local validation passed the full Python/unit/portal suite (1,277 tests
and eight snapshots), production .NET connector regressions, 24 isolated mock
component regressions, five standalone Rust model tests, 18 Rust router tests,
Go CLI tests, and Helm lint/rendered selector/network-policy checks.
These checks do not replace the live-acceptance limitations above.
Release images must also pass CI build, push and keyless signing before
publication. A missing build digest now fails the signing gate explicitly.

## Real Harrier with the same 8-byte source text

Portal pipeline `pip-14d157ab` used registered `mdl-ext-harrier`
(`microsoft/harrier-oss-v1-0.6b`) instead of the synthetic model, retaining a
separate .NET mock source/destination and Rust router. The existing Harrier
service had four ready A100-backed replicas; no model deployment or GPU
allocation was changed. This does not establish equal utilization of all replicas.

100,000 documents with exactly 8-byte text completed in 6.3344142 seconds:
**15,786.8 accepted documents/s**. Batch size was 1,024, concurrency 8,
and vectors were full 1,024D FP32. The destination acknowledged 98 batches
and 409,601,568 binary body bytes, with zero recorded throttles or run errors.
The receipt records `real_embeddings=true` and `persisted_vectors=0`;
the pipeline was paused after completion.

This is real embedding inference with synthetic tiny inputs and a discard-only
destination, not persisted throughput or a result for 1 KiB text. A two-document
preflight through the real registered Harrier route confirmed finite,
nonconstant 1,024D values and the expected FP32 wire shape. This is one completed
Harrier run, followed by the sequential comparison below.

### Native Garnet source to Garnet vector storage

Three sequential registered inline pipelines read native Garnet HASH documents,
called their registered model through the Rust router, and stored embeddings
with the production version-fenced Garnet writer, without Service Bus.
Each processed 100,000 documents with exactly 8-byte hexadecimal text,
batch size 50 and configured concurrency 16. These are different processing
settings from the mock source/sink runs above.

| Model | Pipeline | Dimensions | Elapsed | Stored documents/s |
|---|---|---:|---:|---:|
| Synthetic Rust model | `pip-ae4d5646` | 1024 | 137.857788 s | 725.4 |
| Real Harrier | `pip-321d21a1` | 1024 | 139.751206 s | 715.6 |
| Real BGE-small | `pip-6741cd94` | 384 | 172.592734 s | 579.4 |

Each completed with exactly 100,000 destination vectors and 100,000 source
checkpoints. First/middle/last samples passed dimension, finiteness,
identity/version/model metadata and source-content checks; actual vector
search succeeded. Real-model samples were nonconstant. All pipelines were
paused afterward. BGE used one A100 after an authorized temporary replica
exchange; Harrier was restored to four ready replicas and BGE stopped.

Timing includes initial source population, native polling/read work, model
calls, vector writes and all source checkpoints; discovery warm-up is excluded.
Source population took 0.535, 0.547 and 0.565 seconds respectively. The server
is self-hosted, memory-backed Garnet with no durable-disk guarantee. These are
