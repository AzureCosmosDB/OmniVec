# OmniVec v1.2.1

Patch release for the inline request-size and ingestion image-build fixes found
after v1.2.0. All v1.2.0 features remain included; its documented limitations
remain open unless explicitly addressed below.

## Fixes

- Bound inline embedding requests to 50 texts and 2 MiB of serialized JSON,
  accounting for escaped text and model/pipeline envelope overhead. Large
  documents are divided into smaller request batches without changing their
  source content or output order. This prevents HTTP 413 from model endpoints
  when several 512 KiB documents appear in one change-feed batch.
- Fail explicitly if a single serialized text exceeds the request budget.
  Required embeddings and destination writes must still complete before the
  change-feed checkpoint advances.
- Correct repository-root Docker exclusions to include both .NET ingestion
  and worker projects while excluding build outputs. This fixes the v1.2.0
  change-feed image-build failure.
- Update the PR image-context expectation and add regressions for 512 KiB text
  splitting, JSON escaping, ordering, the 50-text cap, and oversized inputs.
- Correct the existing release-registry scope maps to permit publication and
  pulling of the OneLake watcher repository. This is an external registry
  configuration change, not a credential or wildcard-access change.

## Runtime result

Cosmos DB -> Harrier -> same Cosmos container, inline:

| Documents | Text bytes/document | Persisted embeddings | End-to-end time | Persisted documents/s |
|---|---:|---:|---:|---:|
| 100,000 | 1,024 | 100,000 | 125.520 s | 796.689 |

This used four A100-backed Harrier replicas, 1,024-dimensional vectors and
96,200 RU/s on the benchmark container within the existing 100,000 RU/s account
budget. Insertion took 109.208 seconds; there were zero insertion errors.
101 persisted samples were verified for unchanged content, finite vectors and
nonchunked output. The artificial 12 documents/s producer cap was removed;
64 concurrent inserts, 429 retries and a bounded 5,000-document outstanding
backlog were retained. These are repeated synthetic-text results, not a
universal capacity guarantee.

The 512 KiB run was stopped before reaching 100,000 documents; no completed
100,000-document throughput claim is made for that payload size.

## Deployment and remaining limitations

Use matching v1.2.1 versioned images after their publication succeeds. The
release does not automatically upgrade existing AKS deployments. The byte-aware
change-feed fix was already deployed and exercised in the benchmark environment.

The v1.2.0 limitations concerning startup/storage readiness, inline metrics
attribution, Garnet endpoint normalization, OpenAI base64 response encoding,
native-source lifecycle coverage, and other unresolved test contracts remain.
See [v1.2.0 notes](v1.2.0.md) for details.

Producer pacing, backlog control and outer 429 retries used in benchmark jobs
are session-only benchmark tooling, not new product features. The unvalidated
DSE-Qwen2 adapter and benchmark-specific AKS GPU pinning remain excluded.
